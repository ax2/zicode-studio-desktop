## 工作前先读最新状态

在每轮开始、切换事项、提交/发布前运行 `bun scripts/project-status.mjs`，再读取选中 Issue 的最新正文、全部评论和依赖：

```powershell
bun scripts/project-status.mjs --check-milestones
gh issue view <number> -R ax2/zicode-studio-desktop --comments
gh api repos/ax2/zicode-studio-desktop/issues/<number>/dependencies/blocked_by
```

连续工作每30分钟重新读取；这是活跃工作流程，不创建任何后台定时任务。无法取得最新状态时，不开展新事项或发布，必要的安全收尾继续。不要把网络读取失败当作空项目。

## 决策与同步

1. 用户最新正文/评论、优先级、依赖与版本范围优先于本地旧计划。有冲突先保持数据安全并澄清，不能擅自覆盖用户调整。
2. 同优先级优先处理明确依赖和影响日常使用的问题；负责会话标明分工。浏览器/基础由主会话推进，视觉资产由“视觉资产中心”会话推进。
3. 开始时登记实际负责会话、版本和接下来的工作，将状态标为开发中。互不依赖且修改范围分开的 Issue 并行推进，每项使用独立工作树。主会话负责协调共享文件、构建和集中验收。实现后仍需实际验收的事项标为待验证，达到该 Issue 的验收条件后才标为已完成并关闭。
4. 发生实质进展、失败或阻塞时同步到 Issue，注明源码/构建、验证范围和剩余限制。不要用mock、入口可见、静态检查替代真实业务完成。
5. 只更新本次负责的状态/进展；写入前重读。不要批量重放初始化脚本，不自动改用户优先级、日期、正文或Milestone。
6. 新Issue进入待梳理；范围、验收和模块确认后排期。移出/删除项目的旧Issue不得自动补回；状态脚本只报告未收录项供人工判断。
7. 优先发布经过验证的可用版本，缩短迭代周期。发布前重新读取实时 Milestone，核对本次明确交付的功能与 Windows 安装包。安装启动失败、升级或资料丢失、权限或隐私问题、核心流程不可用和严重稳定性退化应在发布前处理。用户允许后排的低影响问题和可独立交付的增强，记录影响、已验证范围、剩余验收、负责人及后续版本到独立 Issue。已有独立 Issue 可以直接后排，避免重复建单。保留未完成事项和原证据，在发布说明如实列出。发布验证通过后及时发布，并在下一轮继续处理这些 Issue。

8. 每次正式发布后，检查该版本尚未关闭的 Issue，按模块或共用依赖交给专门的 Codex 会话推进。优先复用已有对应会话，其余合并成有明确范围的遗留问题会话。在 GitHub Project 的「负责会话」登记实际会话，并在 Issue 记录原版本、剩余验收和后续排期。会话负责复现、修复、验证和回填证据，达到验收要求后关闭 Issue。主会话负责版本协调和集中桌面验收。

## 桌面验收（用户规则，2026-11-17）

需要独立桌面客户端或原生界面验证时，各会话汇总操作步骤、通过标准和未验证范围到 Studio 主会话，由主会话集中交用户一次验证；不要逐项启动桌面程序、使用 Computer Use 打扰用户，也不要分别请求用户验收。不干扰用户的代码检查、无头自动化和 CI 可继续；需要用户操作的部分在用户完成前保持待验证，其余结果按实际证据如实记录。

## 版本视图与里程碑

- 新定版本时立刻在仓库创建同名 Milestone，并在 Project 建立同名表格视图，使用 `milestone:<版本>` 精确筛选。直接从该版本视图维护范围。已发布版本的视图保留供追溯，全版本可在「版本计划」汇总查看。
- 仓库所有 Issue 都要有 Milestone，包括尚未纳入 Project、已归档及已关闭的 Issue。创建或纳入时即选有版本号的 Milestone。日期可以留空。近期版本放可独立验证的工作，大项及有依赖的事项放到合适的后续编号版本。历史事项用实际交付版本或承接其维护的编号版本。按实际进度调整项目，保留用户已设的版本与优先级。
- 「需求与问题总表」默认用 `is:open -status:已完成` 筛选。审计读取仓库全部 Issue，分别报告无里程碑、未绑定编号版本和缺版本视图。使用 `--check-milestones` 时，缺编号版本或有开放事项的编号版本缺视图会返回失败。仅历史项或空里程碑的缺失视图单独报告，保留 Project 中手工维护的布局。创建或调整版本范围后回读验证。
