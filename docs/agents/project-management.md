## 决策与同步

1. 用户最新正文/评论、优先级、依赖与版本范围优先于本地旧计划。有冲突先保持数据安全并澄清，不能擅自覆盖用户调整。
2. 同优先级优先处理明确依赖和影响日常使用的问题；负责会话标明分工。浏览器/基础由主会话推进，视觉资产由“视觉资产中心”会话推进。
3. 每轮从 GitHub Project 检查当前里程碑可并行的 Issue。依赖已满足、修改范围分开且可独立验证的工作，分派给已有负责会话或子代理，使用独立工作树推进。当前里程碑没有合适的并行事项时，按 Project 优先级继续分派后续编号里程碑中符合条件的工作。
   - 分派前核对已有负责人、依赖与开放 PR。开始时在 Project 登记实际负责会话，将状态标为开发中，并把版本与接下来的工作同步到原 Issue。各事项保留自己的里程碑。
   - 主会话协调共享文件、构建和合并。各负责人回填验证证据，有具体缺口时标为待验证，达到验收条件后标为已完成并关闭。
4. 发生实质进展、失败或阻塞时同步到 Issue，注明源码/构建、验证范围和剩余限制。不要用mock、入口可见、静态检查替代真实业务完成。
5. 只更新本次负责的状态/进展；写入前重读。不要批量重放初始化脚本，不自动改用户优先级、日期、正文或Milestone。
6. 新Issue进入待梳理；范围、验收和模块确认后排期。移出/删除项目的旧Issue不得自动补回；状态脚本只报告未收录项供人工判断。
7. 发布前重新读取实时 Milestone，核对本次必要功能、已知问题和实际 Windows 产物，按下面的快速迭代规则确定交付范围。日常验收候选在本机构建并保存在独立目录。正式发布工作流保留安装器校验和产物回执。正式版本通过必要验收并核对实际附件后再公开发布；发布说明生成器在原说明后列出本版本完整的已完成 Issue 清单和已知问题。

## 快速迭代与验证（用户规则，2026-11-18）

- 各 Issue 负责人在发版前完成与改动相称的验证，将源码或产物标识、检查范围、结果和实际缺口写入对应 Issue。产品变更验证受影响的正常入口和回归，纯文档变更检查内容、差异和链接。遵循仓库现有合并要求。
- 日常开发使用本机定向检查。各负责人可并行完成代码和局部测试，由主会话集中复用构建缓存，按交付批次构建一次 Windows 候选，使用独立资料验证同批功能。修复候选中的问题后，按受影响范围复验。
- PR 与推送 main 只同步源码和项目进展。GitHub 的 Tests、Developer platform 和 Documentation 保留手动检查入口。正式版本标签触发 Windows 打包、安装器验证和发布。
- 复用能对应当前改动和产物的已有回执。新增改动、失败或尚未解决的具体问题需要补验时，补做相应范围。保留历史日志和失败记录。
- 每个发布版本默认围绕一个主要模块，发布已达到验收的工作。冻结前把未开工或依赖未满足的事项移到按模块规划的后续编号版本。已交付的改动及其验收仍归实际版本。影响资料保留、安装升级或关键入口的缺陷可随当前版本处理。
- 每次发版前复核后续里程碑。已达到验收条件、可以合入 main 且适合本版的 Issue 可以一并提前发布。核对发布分支确实包含对应改动，并在发行清单的 extraCompleted 中记录跨里程碑交付。正式发布后同步实际交付版本到 GitHub Project 和 Issue，保留原排期记录。
- 必要功能达到可交付状态后尽快发布，保持小步迭代。已知的资料损失、安装升级失败或核心流程不可用应在受影响版本发布前处理。低影响问题按影响、负责人和后续编号版本记录 Issue，复用已有事项。专项测试和不紧急修复安排在核心功能稳定后推进。
- 主会话负责版本和共享构建协调。提交 GitHub 发布构建后，开发继续按 Project 优先级推进。GitHub 工作流负责构建、必要验收和正式发布。收到用户报告的构建问题后，按对应工作流和提交定位并修复。不轮询发布工作流、不等待构建结果、不安排发布后例行复验。需要原生界面或用户协作的验证，由对应负责人在发版前确定本次改动实际需要的最少操作和通过标准，必要时一次汇总。使用 Computer Use 时遵守用户的桌面与浏览器规则。
- 历史 Issue 按原范围和已有证据关闭，证据尚未覆盖的实际缺口如实保留，并按当前优先级和编号版本推进。关闭历史事项不追加新的验收流程。历史版本、评论和原验证证据保留供追溯。

## Issue 层级与模块基本完成版本

运行 `bun scripts/project-status.mjs` 可查看 `hierarchy`。报告覆盖全仓开放与已关闭 Issue，`roots` 列出顶层路线图候选及目标版本，`rootsWithoutEpic` 列出没有原生父级且未标记为路线图的事项，`rootsWithoutVersionMilestone` 列出目标版本缺失或未编号的根项。无法读取的关系、仓外父项和循环单独列出，供人工核对。此报告只读，不改变发布检查的退出条件。

- 全库 Issue 最多两层。一级对应独立大模块，二级是直接挂在一级路线图下的工作项。开发完成后关闭模块路线图，剩余缺陷、兼容性和专项验收直接归入[缺陷与问题 #140](https://github.com/ax2/zicode-studio-desktop/issues/140)，保留原模块引用。
- 一级路线图使用 `type:epic`。正文写明核心流程及基本完成标准，用较长期的编号 Milestone 表示模块基本完成的目标版本。
- 每个普通 issue 在创建时设置 GitHub 原生 Parent issue，加入 Project，并选择自身实际交付的编号 Milestone。归属通过 Parent issue 和 Sub-issues progress 查看，关闭后保留父子关系。
- 模块基本完成后，新发现的体验改进归入[产品优化](https://github.com/ax2/zicode-studio-desktop/issues/139)，回归和缺陷归入[缺陷修复](https://github.com/ax2/zicode-studio-desktop/issues/140)。正文引用原模块，便于追溯。两条路线图按阶段设定目标版本，后续批次可在新版本建立接续路线图。
- 发版前逐项复核当前版本的剩余工作，已交付且有验收证据的及时关闭。未完成的说明剩余条件并迁往后续编号版本。公开发布后完成发布单及回读，确保该版本没有开放 Issue。
- 项目报告的 `hierarchy.deeperThanTwoLevels` 列出已确认超过两层的 Issue，`openPublishedMilestoneIssues` 列出仍绑定公开 Release 版本的开放 Issue。报告继续只读，不改变已有发版流程。
- 调整范围和发版前，核对开放与已关闭的普通 issue 是否有父项、一级路线图是否有基本完成目标和版本。优先级、负责会话及实际交付状态继续以 Project 为准。

## 版本视图与里程碑

- 新定版本时立刻在仓库创建同名 Milestone，并在 Project 建立同名表格视图，使用 `milestone:<版本>` 精确筛选。直接从该版本视图维护范围。已发布版本的视图保留供追溯，全版本可在「版本计划」汇总查看。
- 仓库所有 Issue 都要有 Milestone，包括尚未纳入 Project、已归档及已关闭的 Issue。创建或纳入时即选有版本号的 Milestone。日期可以留空。近期版本放可独立验证的工作，大项及有依赖的事项放到合适的后续编号版本。历史事项用实际交付版本或承接其维护的编号版本。按实际进度调整项目，保留用户已设的版本与优先级。
- 「需求与问题总表」默认用 `is:open -status:已完成` 筛选。审计读取仓库全部 Issue，分别报告无里程碑、未绑定编号版本和缺版本视图。使用 `--check-milestones` 时，缺编号版本或有开放事项的编号版本缺视图会返回失败。仅历史项或空里程碑的缺失视图单独报告，保留 Project 中手工维护的布局。创建或调整版本范围后回读验证。

## 开发分支与版本回并

默认开发入口为 main。已发布版本由公开 Release 标签标识，可以在独立工作树精确复现。v0.7.0 的集成以公开标签 90cefeb 为第二父提交，保留 main 上的 Project 层级报告、Windows 候选输入检查和官方 Cargo 源配置。

从 v0.7.1 起，已分叉的版本线以该版本实际发布的不可变标签为准，通过一个保留双亲的合并 PR 单向回并 main。冻结前将已核对的本版交付范围纳入版本分支。待发布分支上的其它提交继续留在该分支。回并前检查标签是否已是 main 的祖先，审查两侧独有变更，并复用范围与提交匹配的验证回执。

后续新事项从已同步的 main 开分支。需要同时维护冻结版本时，先在最早需要的版本分支修正一次，随发布标签回并 main。另有未发布工作时，从选定的稳定提交建立版本分支，按本版交付范围逐项纳入。完整验证、正式发布与修改公开标签各自独立。
