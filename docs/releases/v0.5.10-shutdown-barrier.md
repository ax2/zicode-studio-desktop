# HTTP 服务释放与 Host 关闭屏障

关联 Project #4 / Issue #5。2026-11-13，Windows。

## 失败与原因

不可变候选 `v0.5.10` / `45d250037461a1effdd6230b3ec14119835039b0` 的 GitHub run `43390188894` 在主 Rust 测试中 912 通过、1 失败、57 忽略。`workspace_close_waits_for_staged_export_and_blocks_later_writes` 的导出完成和关闭后拒绝写入通过，随后 `Host state still owned after shutdown barrier` 失败。未生成安装包，草稿和原标签保留，未公开或设置 Latest。

同一冻结源码在本机单次 Cargo 执行通过；随后直接执行刚编译的同一测试二进制，第一次就复现相同断言。不能把单次绿灯当作问题消失。证据：主会话 `outputs/shutdown-barrier-baseline.log` 与 `shutdown-barrier-baseline-repeat.log`。

当前锁定的 axum 0.8.9 `src/serve/mod.rs::handle_connection` 在连接任务末尾先 `drop(close_rx)`，再隐式销毁连接/服务。监听器等待该关闭计数器后可以先返回；先前 Host 只跟踪监听器及显式任务，不能保证每个连接服务已释放其 `Arc<HostState>`。这使数据库所有者的释放晚于关闭屏障。

## 修复边界

独立 `fix/release-shutdown-service-barrier` 分支新增 `lifecycle_service` 模块：每个连接服务及其克隆持有生命周期 lease，请求 future 也单独跟踪。结构体先销毁内部服务，再释放 lease；请求沿用 Tokio 的 `TrackedFuture` 以保证同样的释放顺序。loopback、tools-only worker、LAN TLS、公开 TLS 和 enrollment 监听器使用一致适配。

不改变 HTTP 业务、权限、协议、关闭超时或原有严格断言，不加 sleep/retry 掩盖状态残留。未改个人 selector、资料、版本或 frozen tag，没有重建/替换日常 EXE。
