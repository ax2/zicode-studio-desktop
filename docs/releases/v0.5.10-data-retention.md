# Issue #31 Windows 数据保留验收

## 2026-11-13 当前进展

完整离线恢复已独立提交，缺失快照的原生保留/撤销/重启及默认保留、关闭不撤销均已验证。见[撤销记录](../iterations/2026-11-13-restore-cancel.md)和[默认动作补验](../iterations/2026-11-13-restore-default.md)。下文保留早期方案和各批次证据的时间顺序；其中“待检查/拟接线”已由上述新记录更新，不能当成当前失败。普通selector、最终发行包升级和完整进程中断链路继续待验收。

## 准备独立资料

在 Windows 测试账号或虚拟机内运行。使用同一个测试账号依次启动 v0.5.9 和最终 v0.5.10 候选。记录两版安装包和 EXE 的 SHA-256、源码版本、进程路径及启动时间。退出时核对本轮启动的 PID、路径、时间和 EXE 摘要。

```powershell
pwsh -NoProfile -File scripts/qa-windows-data-retention.ps1 -Phase Initialize
```

脚本在本 checkout 的 `.cache/task-scratch/issue-31-data-retention` 下创建合成资料目录、所有权标记和 selector 模板。在测试账号实际的 LocalAppData 中放置该模板，文件名为 `zicode/desktop-profile.json`。用普通入口启动以验证 selector。显式传入 `--isolated-profile` 可用于独立开发预检，但会绕过 selector。使用 selector 的真实验证应在独立账号或虚拟机中进行。

用 v0.5.9 创建一条合成笔记并附加小文本文件，创建合成书签、安装离线测试插件、导入自制 PNG，注册独立的合成工作区并记录其 ID。记下各入口的可见内容及附件、PNG 的 SHA-256。退出基线应用后执行 `CaptureBefore`。从最终候选的普通入口重新打开，核对相同笔记和附件、书签、插件状态、图库原件与工作区 ID/路径；退出后执行 `CaptureAfter`。脚本记录默认工作区笔记及附件、浏览器、插件、图库和工作区注册数据库的相对路径、大小及 SHA-256。SQLite 迁移等合法写入也会产生字节差异，必须逐项通过应用里的记录或数据库只读检查解释，不能把差异直接记作数据丢失或跳过检查。外部工作区内容另行核对。

关闭测试实例后，把测试资料目录暂时改名，保持测试账号的 selector 指向原路径。启动候选，记录报错、退出及原路径未重新创建的证据。恢复目录名后再次启动并检查原数据。

## 备份和中断恢复

用测试工作区创建应用内备份，再修改笔记和附件。恢复该快照后核对旧内容与附件摘要，再检查自动创建的恢复前快照可以找回较新的内容。核对快照只含受支持的工作区应用目录。浏览器、插件、图库和工作区注册信息在升级步骤独立核对。全程使用合成资料，凭据许可保持缺省。

另外安排一次可确定命中目录交换间隙的中断测试。记录进入交换阶段的证据、启动进程身份、终止点及重启后各应用目录状态。一次成功恢复或在备份阶段终止进程都不能证明交换阶段恢复有效。

在真实进程硬中断测试之前，可以先在新合成 profile 执行 `StageInterruptedRestore`，放入已移走原笔记、尚未安装快照的磁盘状态。使用带启动接线的 EXE 和 `--isolated-profile <profile> --tools-only` 启动，再执行 `CheckRecovered` 确认原始字节已恢复。该步骤验证真实桌面进程在启动时接手既有事务。

### 离线恢复验收

1. 用独立 profile 启动含离线恢复接线的 Windows 候选。在备份设置中创建一份包含合成笔记和附件的快照，修改两者，并记录当前文件的 SHA-256。
2. 在设置页选择旧快照并确认恢复。记录页面显示「已排队」及磁盘上的 `system/workspace-restore-request.json`。再次读取笔记和附件，确认当前内容和摘要仍一致。尝试删除所选快照，确认操作被拒绝。
3. 正常退出本轮启动的候选，验证进程已退出，再以相同隔离资料启动。记录 `system/workspace-restore-result.json` 中相同的请求 ID 和恢复前快照 ID，确认待执行请求已清除，设置页显示恢复完成，笔记和附件恢复到所选快照的摘要。
4. 再次正常退出并启动，确认请求没有重复执行。将恢复前快照排队，再完成一次重启，核对较新笔记及附件可找回。
5. 验证旧工作区时，在合成注册表中加入一个独立根，并仅在其 `.zicode` 中放置合成事务。确认候选按注册关系处理事务，同路径别名只处理一次，未注册目录及其他旧资料保持原位。

后台进程测试单独使用合成资料或隔离测试进程。已有 Worker 应收到停止请求并完成排空，恢复端持独占锁时新 Worker 无法启动。旧版只持实例锁的 Worker 也必须退出。验证停机超时时待执行请求及原始摘要仍保留，并确认恢复没有设置更新后自动重启 Worker 的标记。

本机隔离预检可用 `SeedOfflineRestore` 和 `ChangeOfflineRestore` 生成两组固定字节。排队后执行 `CheckRestoreQueued`，重启后执行 `CheckRestoreApplied`。这组文件用于验证快照字节及磁盘回执，最终候选仍需核对通过笔记界面创建和读取的真实笔记。

损坏或丢失快照可能让现有启动路径重复失败。后续需提供启动失败界面上的明确撤销入口。撤销须持维护租约，先收敛未提交事务，再按请求 ID 核对仍待执行的请求，保留原资料与快照。已提交但未发布的事务应补发结果。验证损坏快照能撤销并重新启动，以及回滚无法确认时保持现场。

拟接线：由 `setup_native_runtime` 传递结构化的恢复启动错误，只对仍待执行且已确认没有已提交回执的请求提供撤销。现有 `.setup` 启动错误分支显示原生「撤销恢复请求」和「保留请求」选择，默认保留。确认后在后台重新取得 `automation_worker::stop_for_restore` 租约，调用备份模块的 `cancel_startup_restore(expected_request_id, workspaces)`；成功后提示用户手动重启。该动作通过原生对话框完成，可沿用现有启动错误入口，无需新增 Tauri 命令。一般启动错误继续走原有界面。

撤销函数需持 system 请求锁，重新读取请求 ID、核对注册资料根，处理未提交事务并再次检查提交标记。已提交事务只允许补发回执；冲突 ID、回滚不确定、根不可确认或维护租约超时均应保留请求。确认安全后将请求在同目录原子改名为带请求 ID 的取消回执。验收需覆盖失效快照、同一请求重试、不同请求冲突、提交后未发布结果、回滚失败与维护租约超时。
