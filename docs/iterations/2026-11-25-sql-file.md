# v0.7.9 · SQL 格式化文件导入与结果下载

在工具中心打开冻结 ZiDevTools Text 0.4.1 的「SQL 格式化」，点击「导入 SQL 文件…」。选择的 `.sql` 文件须为 UTF-8 且不超过 8 KiB，UTF-8 BOM 可用。导入只替换 SQL 编辑区，可撤销。点击「执行工具」才格式化，原文件保留。空白、错误后缀、超限、编码无效和读取失败都保留现有输入。

格式化成功后，点击「下载格式化 SQL」。Studio 将本次返回的完整 SQL 文本交给现有下载流程，建议名称为 `formatted-sql-<时间戳>.sql`。改动当前输入后需要重新执行。格式化继续使用通用方言和默认布局。独立版的 PostgreSQL/MySQL/SQLite/SQL Server 选项、缩进、大小写和更大文件仍由 [#28](https://github.com/ax2/zicode-studio-desktop/issues/28) 跟踪。Windows 桌面下载体验及实体系统文件窗口保留集中验收。

## Windows 验证

- 独立 Text 0.4.1 候选 02 共 112 文件，1,032,175 字节。目录索引 SHA256 `7c6b1a226526eb35eb0acc4a0d571652bc29049e9cf5bd8d18267c55a39dde9f`。WASI SHA256 `7cfcde63aaaa68353067ca1f7a99c8c6e4a6926166f541a6de03c7c814803767`。用 Studio 独立核验器核对全部文件。
- 正常工具中心资源和冻结清单通过 1180px 英文浅色及 420px 中文深色。两种视口均验证带 BOM 的本机文件选择、取消、撤销、无效 UTF-8、超限、含中文的注释与字符串、尾部空白、原件逐字节回读，并使用生产 Windows Worker 手动格式化三次。三次输入分别为原 CRLF、真正修改后的 LF，以及恰好 8192 字节的 SQL。
- 初次浏览器实测发现，HTML 编辑器仅把 CRLF 显示成 LF 时，失焦事件被当作编辑，导致清掉撤销信息，并将原 CRLF 替换成 LF。修复后，归一化后的相同可见内容不覆盖编辑器原值和撤销，实际改变文本仍按编辑器值提交。共享文本、JSON 与工作台回归一并核对。
- 定向回归 110 项及共享输入控件 13 项通过。包含真实生产 Worker 的 JSON Schema 与表格流程、共享普通文本和结构化 JSON 文本区。类型、全仓前端检查和 5488 个中英文词条通过。正式工具中心资源 SHA256 `755b6d60cbe527586e9d2c0d34041822939e3ace3b680980ea46afc6c8bf005f`。
