# 插件任务状态存储（2026-10-17）

## 目标与范围

为 `plugin.task.lifecycle.v1@1.0.0-preview.1` 准备 Studio 自有的持久状态底座。本阶段先新增内部 `plugin_task_store` 模块，随后接入可信 Host 只读路由与任务中心空状态界面；尚无调度操作处理器或插件 profile。DevTools 全量工具接受数仍为 0/154。

## 实现

- 独立 SQLite schema 版本 1；按 workspace、scene、plugin、包版本、profile 版本和 operation 验证所有者；相同幂等键与输入返回同一任务，输入不同则冲突。
- 只保存有界输入的 SHA-256，不持久化输入正文。任务事件只记录状态、时间和递增序号。
- 状态转换受限，终态不可更改；取消请求与实际停止分开。重启时原本 `running` 的任务转为 `interrupted`，不自动重复执行。
- 每插件活动任务上限 128、每工作区记录上限 1000、每任务保留最近 256 条事件；旧游标要求重新获取快照。终态记录有 30 天保留规则。
- 初版模块没有连接真实数据库路径；后续只读 Host 路由已按需连接独立数据库。确认绑定、权限撤销、操作调度和结果传递仍需实现并验收。

## 保留期修正

后续审查发现，原实现先查幂等键再清理 30 天前的终态记录，使重复请求可以让过期任务长期保留。现将同工作区的过期终态清理移到幂等查询前，增加“旧终态键到期后可重新创建任务”的测试。未过期任务的幂等行为不变；在保留期外重复同一键会得到新任务，后续 Host 路由需要明确告知调用方该窗口。

本次修正后 `bun run check:rust:static` 再次通过（仓库格式检查仍为既有 advisory，新文件单独检查通过）；只读空间扫描 target 从 29,399,920,143 B 增至 29,399,934,479 B（+14,336 B），task-scratch 838,287,896 B 未变。没有清理共用缓存。

## 启动清理补齐

存储复核还发现：若工作区不再提交任务，已过 30 天的终态记录不会因其他工作区的提交而清理。现把全库终态过期清理加入数据库打开事务，和运行中任务的 `interrupted` 恢复一同完成；排队和等待确认的活动记录不因年龄被删除。持久化测试扩展为同时包含过期终态和旧排队记录，验证重开后分别清理与保留。该清理仅作用于独立插件任务数据库；当前 Host 尚未启用该数据库，不会触碰已有应用或插件数据。

复测 `plugin_task_store::tests` 为 7/7 通过；`bun run check:rust:static` 通过（全仓库格式 advisory 持续，新文件单独 `rustfmt --check` 通过）。只读前后扫描 target 从 29,399,934,479 B 到 29,400,012,815 B（+78,336 B），task-scratch 838,287,896 B 未变；没有删除缓存。卷可用空间变化受其他进程影响，不归因于本次检查。

## 重启后排队任务的真实状态

进一步核对发现，当前没有可恢复排队任务的操作处理器，但数据库重开时把旧 `queued` 状态原样保留，会让任务中心永久显示无法执行的排队任务。现与原 `running` 恢复规则一起，在数据库打开事务中将两者转为 `interrupted`，各追加一个严格递增的状态事件。旧排队任务在本次中断时才进入终态，30 天保留期从该时点开始，供用户查看失败原因，不按旧的排队时间直接删除。

2026-10-17 补充：当前也没有重启后恢复确认步骤的处理器，旧 `awaiting_confirmation` 不能继续保持活动状态或复用确认。数据库重开时现将它转为 `interrupted` 并追加事件，保留为只读历史；未来真正的恢复机制必须重新验证操作和授权。定向持久化测试 1/1，Rust 静态检查通过。第一次定向编译因新增测试夹具插入相邻测试而未通过，移入正确测试后复跑成功；保留这次失败事实。
