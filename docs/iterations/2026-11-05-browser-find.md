# Windows page search — 2026-11-05

The browser overflow menu now opens a compact in-flow page-search row. The trusted Studio chrome also handles Ctrl+F; the input supports Enter/Shift+Enter, Escape, previous/next buttons, a match counter and case-sensitive search. Closing the row returns the space to the page. Search closes when changing tabs, navigating/reloading or leaving Browser.

Search uses WebView2's native Find API, without evaluating query text as JavaScript or rewriting the document. Requests stay within the requesting Studio window and its owned tab. The Host accepts at most 1,024 UTF-8 bytes and rejects embedded NUL; the visible input permits 256 UTF-16 units. Queries are transient and not saved in browser metadata. Unsupported runtimes receive an explicit error without preventing ordinary browsing. The native API is documented in the [official Find reference](https://learn.microsoft.com/en-us/microsoft-edge/webview2/reference/win32/icorewebview2find?view=webview2-1.0.3537.50).

Start waits for native completion with a 10-second response bound, suppresses the default native dialog and requests highlight-all. Native count/index are read after Start and refreshed every 350ms while the custom bar remains open. Operations are serialized; polling stops on close/error and skips reads when the chrome document is hidden. Epoch checks discard results belonging to old queries or tabs. Composition-aware input is debounced. Stop is queued after pending work before a tab transition.

Escape, menu entry, completed reload, completed tab switching and Browser–Notes–Browser routing all cleared search as intended. All six baseline tabs and recently closed entries remained exact.

A second process preserved the full tab state and bookmark library, with search initially closed and zero native matches. Both the previous baseline note and the newly saved Notes-layout fixture retained exact title/content. A real Win32 minimize/restore cycle preserved tab state and native page presentation without stale viewport errors. On this runtime document.hidden stays false during native minimization; the test uses the actual Windows minimized state instead and makes no claim that the controller's IsVisible flag becomes false while its parent is minimized. Both owned processes exited normally and the debugger closed. The daily installed app and actual user profile were not replaced.

## Recovery fixes and retained failures

The first acceptance waited for Browser but saw Notes despite a browser URL. Explicit Browser navigation worked, and the next fresh process started in Browser correctly. This first-launch route discrepancy remains unexplained and is recorded for follow-up rather than called fixed.

The old resize helper selected Process.MainWindowHandle, which on this process was the hidden single-instance helper window. It now requires one visible Studio-titled window owned by the receipt-verified process, restores native minimized/maximized state and resizes that exact window. The failed resize and initial route records remain available. The hidden/minimized setup also exposed a stale viewport-error message. Browser surface synchronization now defers creation while the document is hidden, shares concurrent creation requests, rechecks the selected tab and geometry after creation and clears only a successfully recovered surface error. A dedicated regression verifies these cases. Native hidden/restore synchronization is based on document visibility; Windows minimize behavior has the narrower scope above.

A later harness returned to the original tab before it had awaited the intermediate tab's saved/visible state, so its original-tab check could pass before either transition completed. Instrumented hidden-property stacks showed normal transition closure. Final acceptance waits for both saved selection and native presentation on each tab. Reload also waits for the actual successful navigation-finished event. Original failures are retained; the product assertions were not relaxed. The first minimize harness incorrectly assumed document.hidden must follow Win32 minimization; its failure is retained alongside the corrected native-state receipt.
