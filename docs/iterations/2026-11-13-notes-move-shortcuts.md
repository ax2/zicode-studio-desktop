# Move Notes shortcuts without losing their scope — 2026-11-13

Part of [Issue #22](https://github.com/ax2/zicode-studio-desktop/issues/22), which remains open.

## Confirmed problem and fix

The actual Windows UI showed that moving a note kept its body and attachments but left recent/pinned shortcuts pointing to the old notebook. An old copied note link also returned `Note does not exist`; that separate Host/reference problem is **not fixed by this change**.

After a successful Host move, the frontend now applies one transactional shortcut action to both recent and pinned lists. It replaces only the exact source notebook/note pair, keeps order, removes duplicates and preserves an imported same-ID note in another notebook. A rejected move does not rewrite references. A completed move belongs to the workspace where it was requested even if the user has navigated elsewhere; only that workspace's IndexedDB record is updated, and the current workspace UI is untouched. Storage failure keeps the update queued for the existing refresh/retry flow.

Changes stay in `shortcut-repository.ts`, `note-shortcuts.ts` and `editor-mutations.ts`. The deliberate large-file exception in `notesStore.ts` is one composition argument connecting the callback. Only the Notes feature bundle was rebuilt using the project's existing esbuild settings, avoiding the concurrent Visual Asset bundle.

- Complete Notes frontend suite: 185 tests / 8 files passed. TypeScript and final frontend/design checks passed with existing repository warnings. No native rebuild or Rust changes for this patch.
- Actual Windows debug SHA256 `6191D80B2DC40D4113D36FE99FDF07A83F88E7374F1BD28031CFFC46DFBDE91B`, explicit isolated synthetic profile, real Host and IndexedDB. The normally served Notes bundle matched current main-source generated bytes.
- A newly pinned note was moved through its management menu. Both recent and pinned references changed to the new notebook; the pinned entry opened it. Unpinning exposed the recent entry, which also opened it. Repinning worked at the canonical location.
- Delete required a second confirmation: the note remained readable before it. The real trash UI restored the note with exact body, ID and original binary text-attachment bytes. The prior baseline note stayed byte-for-byte equivalent through Host reads.
- Normal process exit and restart retained the new pin, exact restored note and attachment bytes. The pin still opened the note. All owned test processes exited normally; the daily app and personal profile were not accessed.

Evidence in session `outputs/`: `notes-references-reproduction.json` and the preserved first translation-expectation timeout; `notes-shortcuts-native.json`, `notes-shortcuts-restore-native.json`, screenshots and exit receipts. The first restart harness tried the hidden desktop Activity entry before resizing; the corrected harness resized the owned window before interaction. The old-state bug is proven by the native reproduction.

## Remaining scope

Previously stale shortcuts and copied incoming note links still lack an authoritative durable relocation. The screenshot intentionally retains the old fixture's unresolved-shortcut warning; it is not evidence of all historical references being repaired. A future fix must preserve notebook provenance and backup/restore behavior: backup imports retain note IDs, and bounded/filtered lists cannot prove a unique global match. Do not guess by UUID or rewrite unrelated imported notes. A crash between Host move completion and the frontend persistence also requires that authoritative recovery path.

Late move-failure rollback coverage and final candidate/upgrade acceptance remain open under #22/#31. No installer was generated or installed for this patch. No schedules, paid models, credential changes, or other-platform builds.
