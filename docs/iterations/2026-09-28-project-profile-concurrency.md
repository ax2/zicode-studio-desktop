# 项目上下文多窗口并发保护（2026-09-28）

## 目标与依据

前一轮已防止损坏文件被空配置覆盖，但同一项目的多个窗口仍可能按最后一次保存覆盖对方修改。任务存储已有 SHA-256 修订号、独占锁和同目录原子写入约定，本轮让项目上下文沿用相同语义。

## 修改

- 读取项目上下文时返回对应文件字节的 SHA-256 修订号；文件不存在时使用固定的缺失态修订号。
- 保存必须携带读取时的修订号。宿主取得 `.lock` 独占文件后重新读取并比较；冲突、锁被占用和缺少修订号分别返回稳定错误码，原文件均不改动。
- 成功写入前保留有限历史快照，再写入同目录临时文件、同步并重命名；返回新修订号给窗口。
- 前端按项目保存修订号。保存冲突时保留正在编辑的草稿，提示刷新；刷新后的已保存版本可在编辑页展开对比。项目切换重置局部错误状态。
- 将项目上下文文件大小上限调整为 256 KiB，以容纳最多 50,000 个 UTF-16 字符的中文说明。

## 验证与限制

扩展、React 和 CSS 构建通过；TypeScript 类型检查、`bun run check`、i18n 覆盖检查、MkDocs 严格构建及 `git diff --check` 均通过。`bun run check` 保留现有告警，其中设计检查报告一处内联样式告警。现有项目上下文测试夹具已按修订号协议更新；本轮未运行测试。

应用内写入由锁串行化；不遵循该锁的外部编辑器仍可能在校验与重命名之间修改文件。崩溃遗留的 `.lock` 需在确认没有其他写入进程后人工处理；跨平台实机并发与故障恢复仍待验收。

## 接续：冲突后的定向刷新

项目上下文页增加“刷新已保存的上下文”，只读取当前文件及修订号，保留本窗口未保存的草稿供对照。读取失败继续显示错误并阻止保存。前端以递增读取序号丢弃过时响应；项目切换或保存成功时也使此前的读取失效，避免旧响应覆盖新修订号。

React 构建、TypeScript 类型检查、`bun run check`、定向 Biome 检查、i18n 覆盖、MkDocs 严格构建和 `git diff --check` 均通过。全局检查保留现有告警。本轮未运行测试，跨窗口实机操作仍待验收。

## 接续：保存期间继续编辑

发现保存按钮等待宿主响应时，说明、场景和预算输入仍可编辑，而成功响应会无条件清空 `contextDraft`，导致请求发出后的新输入消失。现记录草稿变更序号：保存成功只清除提交时的草稿；等待期间发生过编辑则保留后续草稿，并提示仍有未保存修改。项目切换也递增目标序号，旧项目迟到的保存结果不再写入重新打开的同名项目状态。

React 构建、TypeScript 类型检查、`bun run check`、定向 Biome 检查、i18n 覆盖、MkDocs 严格构建与 `git diff --check` 均通过；全局检查保留现有告警。本轮未运行测试；快速连续编辑、窗口切换与跨平台实机交互仍待验收。
