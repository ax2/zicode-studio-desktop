# Stage：插件业务失败提示与隔离（2026-10-17）

## 目标与发现

ZiDevTools 图片缩放候选的真实 Host 用例已证明：损坏图片返回 HTTP 200、
`result.ok=false`、`INVALID_IMAGE`，无派生资源；随后另一接收工具仍可执行。
但 Studio 的目录资源工具和跨工具接力弹窗把这类业务失败显示成
“接收工具已完成，结果尚未保存”，容易误导用户。旧前端测试仅核对失败
不写入最近使用，没有检查状态文字。

## 修改

- 两个可信父界面在合法响应 `result.ok === false` 时显示
  “工具返回错误，已保留输入，未保存任何结果”；结果内容仍以文本方式展示，
  不渲染插件 HTML，不调用成功历史回调。
- 保留已确认的输入/参数与再次运行入口，不自动重试。协议损坏或响应丢失仍
  走独立的调用恢复流程，不当作普通业务错误。
- 为两处既有失败测试补上状态、无成功状态和重试入口断言；接力测试使用
  完整 Host 响应中的 `ok:false`，保留第一次不完整 mock 导致的失败记录。

## 同日后续：当前 Debug 原生失败与隔离复验

复用 `.cache/task-scratch/trace-native-20261014/profile` 中已启用的 0.1.1 图片候选及现有 8 字节合成 PNG 签名样本。当前 0.4.2 Debug EXE SHA-256 `C2856DF5F486D10FF4D716751365D51AC436AB50500AD6AC0B7AEC7FA383E3EC`。通过 `--open-file` 进入工具目录，不使用原生文件选择器；目录显示 24 个工具，其中按文件资源筛选为 3 个。打开“缩放图片”，选择已打开文件，核对名称/8 字节，明确确认提供，填写 `png`、最大宽度 `2`、质量 `85` 后执行。

真实 1442×931 Windows WebView2 窗口显示“工具返回错误，已保留输入，未保存任何结果”，原始结果 `ok:false`，公开错误码为 `IMAGE_OPERATION_FAILED`、公开消息为“图片处理失败或超出运行资源限制”；没有派生输出或保存操作。此前 Host 用 `not a PNG` 字节得到 `INVALID_IMAGE`，本次样本仅为 PNG 头部，二者不是相同输入，不能把错误码差异归为回归。失败后目录仍可操作；打开独立 ZiDevTools 文本插件的 Base64 解码，以 `YQ==` 得到成功结果 `a`，证明此原生场景中图片调用失败未阻断另一插件工具。

还曾将同一坏图交给内置 `Inspect image resource`；它返回 `resource_input_invalid` 并进入“执行结果尚不确定”，按界面“停止/恢复调用”后显示已确认执行结束、未恢复原结果。这是该无效资源的独立恢复路径，不计为成功执行，也不据此断言确定性输入拒绝的分类正确。上述界面截图均即时目视检查，未导出 screenshot payload。跨平台、签名正式包、崩溃注入和完整 154 工具接受仍待。
