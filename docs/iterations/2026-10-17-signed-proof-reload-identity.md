# 签名插件证明身份与重载（2026-10-17）

## 目标与发现

注册表发现签名插件时会重新验证签名、发布者与已安装文件，但执行代次比较此前只保留发布者身份、包路径和解析后的清单。如果外部程序用另一份有效签名包及配套证明替换受管目录，保持相同 ID/版本/发布者与清单字段，显式重载仍可能沿用旧游标和活动任务。

## 修改

- 签名插件发现时只读取一次安装元数据，先验证包、证明和发布者，再从已验证的完整性证明计算 SHA-256 指纹，记录进程内内容身份。验证失败或缺少证明时，该插件保持不可发现并输出原有诊断，不接受无证明身份。
- 证明指纹参与现有执行代次比较。另一份有效签名证明使该插件执行代次轮换，Host 沿用已实现的精确撤销逻辑；同一份证明重载保留代次。无需改动插件容器格式、DevTools 工程或应用版本。

## 验证

- 注册表专项 1/1：安装接收端测试签名包后，同证明重载保留代次；外部放入另一份有效签名包和对应证明、保持相同 ID/版本/发布者/解析后清单，重载轮换该插件代次，`core.chat` 保持不变。
- 原有签名安装、升级、回退、发布者撤销专项 1/1。
- `bun run check:rust:static` 退出 0；Cargo check 与严格 Clippy 通过，rustfmt 仍为 advisory。
- 前后只读空间扫描完整、未知项 0：`target` 29,419,827,625 → 29,419,844,521 B；task-scratch 均为 852,978,182 B；E 盘可用 45,563,518,976 → 45,549,817,856 B。未清理文件，卷空间变化不归因于本阶段。

## 边界与遗留

这是进程内重载代次，不是对外部文件并发改写的事务隔离；包执行前和结束时仍分别做完整性验证。真实 DevTools 提供方签名包、原生界面发现→加载→执行→展示、全部工具和跨平台验收仍待，完整 DevTools 工具接受为 0/154。

后续已用真实 Host HTTP 验证重载的精确游标与任务作用范围，见 [签名证明变化的 Host HTTP 重载验收](2026-10-17-signed-proof-host-reload.md)。正式提供方和原生界面边界仍待。
