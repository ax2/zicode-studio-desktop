# 2026-09-29 工作区备份恢复暂存

状态：实现与静态检查完成；真实桌面恢复验收未完成。

## 目标与发现

- 原恢复逐个删除当前应用目录，再从备份复制。来源读取或复制失败时，当前目录已经丢失，且较早的应用目录可能已被替换。
- 现有回退快照可供用户再次恢复，但不能使本次失败自动回到原状态。

## 修改与决策

- 先将备份中所有可恢复应用目录完整复制到工作区 `.zicode/.restore-<随机 ID>/next/`。该阶段失败时不修改当前应用目录。
- 暂存完成后创建恢复前快照，保留已选来源；逐个把旧目录重命名到暂存区 `previous/`，再把准备好的目录重命名到原位置。替换阶段失败时按相反顺序尝试回滚。
- 回滚成功时清理暂存并报告失败；回滚不完整时保留暂存目录及原数据，错误中给出位置以便人工处理。成功后清理暂存目录；若清理失败写日志，不把已完成的恢复报告成失败。
- 暂存目录位于目标 `.zicode` 内，目录交换不跨文件系统。恢复前快照仍由原有机制管理，成功后的来源与回退快照保留策略不变。
- 界面区分“替换失败但原目录已放回”和“自动回滚未完成”。后者保留暂存目录路径并提示暂停使用工作区；中英文帮助同步说明人工检查边界。

## 验证与遗留

- `cargo check --locked`、`cargo clippy --locked -- -D warnings`、本轮 Rust 文件 rustfmt 检查与差异空白检查通过。本轮不新增或运行测试。
- 回滚提示接入后，`bun run typecheck`、`bun run check`、React 构建、CSS 打包与 i18n 覆盖检查通过（2686 个中文词条，无缺失）；Rust 编译、Clippy 与目标文件格式复查通过。Biome 与设计检查仍显示仓库其他现存的非阻断提示。未运行测试。
- 目录交换不是跨应用原子事务。进程崩溃或断电发生在交换中途时，暂存目录可能含旧目录，仍需人工恢复。运行中其他写入者、打开的 Windows 句柄以及三平台真实文件系统行为尚未验收；这些因素可能导致重命名或回滚失败。
