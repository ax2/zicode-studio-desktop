# v0.7.9 · UTF-8 与 Hex 文件转换

「UTF-8 → Hex」可导入 8 KiB 内的 UTF-8 文件。执行后下载大写、空格分隔的十六进制 TXT。编码保留原文件的 BOM、换行和控制字符。

「Hex → UTF-8」可导入 8 KiB 内十六进制文本。文件选择器优先显示 `.txt` 与 `.hex`，导入会识别编码 BOM。Worker 沿用既有规则，支持成对十六进制字符、大小写及 ASCII 空白分隔，输出须为有效 UTF-8。成功后可下载完整 TXT，包括有效空结果。

导入可撤销。执行和下载分别由用户触发，源文件保留。8 KiB 的编码输出可能超过解码入口的文件上限，实际输入按两个入口各自的原文件字节数核对。

## Windows 验证

- 使用冻结 Transforms 0.1.1 候选 01 和生产 Windows Worker。804 文件、实际隔离 Windows Host、本机 Pi 工具通道与 23 个固定样例／十个授权阶段见[同包验收](2026-11-25-line-tool-files.md)。
- 正常工具中心 1180px 英文浅色、420px 中文深色共实际运行 16 次，10 次成功，6 次预期拒绝。27 字节正文含 BOM、中文、表情、CRLF、制表符、NUL 和尾空格，转成实际下载的 Hex 后，混合大小写及空白分隔仍能精确还原。原件与折行版本逐字节保留。
- 两个方向均实际用 8192 字节文件执行。编码结果完整下载为 24,575 字节，SHA256 `09fa4e8169ebd47d891c09dccd767aefa9170b00b76a1a2353a9609f503ea6fa`；解码结果为 4096 字节。10 份下载逐字节等于同次 Worker 输出。覆盖零字节结果、奇数长度、非十六进制字符和无效 UTF-8。初轮自动化错误断言已按冻结合同修正为 `INVALID_ENCODING`。
- 68 项定向前端、4 项矩阵通过，8 项既有跳过；TypeScript 和词条覆盖通过。生成工具中心资源 SHA256 `58f47968f0c96020f347a5c087a4e394a9e8105b4b0f51ee0e7d6b37430f1fb2`。

较大文本、二进制文件、Windows 原生文件选择窗口与安装版桌面下载体验由 [#28](https://github.com/ax2/zicode-studio-desktop/issues/28) 跟踪。
