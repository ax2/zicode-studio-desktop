# 2026-09-30 全工作区自动化调度设计调查

状态：桌面 Host 已接入全工作区到期入队、免审批派发、运行结果回写、失败重试和丢失进程识别；应用退出后的持续执行及三平台真实运行仍未验收。本文保留初始调查和各轮实现记录。

## 目标

应用打开期间，所有已注册且可访问的工作区的到期规则都能进入对应任务队列，用户无需逐个打开项目或切换窗口。应用完全退出后的无人值守执行属于单独的常驻服务生命周期，不由页面定时器承诺。

## 当前实现边界

- `HostServer` 生命周期已启动 `automation_schedule`、`automation_dispatch`、`automation_runs`、`automation_orphans` 与 `automation_recovery`，分别处理到期规则、已入队任务、结果、丢失进程与重启恢复。桌面清单仍是只读展示入口，调度由这些独立的 Host 任务执行。
- 应用退出后没有常驻调度服务；通知、文件并发、休眠唤醒及 Windows/macOS/Linux 的实际运行尚未完成实机验收。页面定时器仍存在，重复入队依赖稳定任务 ID 与文件修订号保护。

## 初始调查证据（历史）

- `frontend/src/features/automation/store.ts` 的定时器只从当前 Pi 目标读取 `automation_workspace`。`public/native/app.js` 在页面生命周期启动它；切换工作区时触发新工作区检查。
- `src-tauri/src/main.rs` 的 `list_workspaces` 能列出元数据中所有已注册工作区。Host 启动时把存在的工作区目录注册进 `HostDataPlane`，后者维护可更新的 `workspace_roots` 映射。这个映射比页面当前目标更接近全工作区范围，但仍须处理目录离线、删除和恢复。
- 正式规则位于 `<workspace>/.zicode/automation/workflows.json`，任务位于 `<workspace>/.zicode/tasks/tasks.json`。Pi 扩展目前拥有两份文件的读取、迁移、修订号、锁和原子写入逻辑；Rust Host 尚无等价的自动化写入接口。
- 自动派发由页面内 `super-agent-runtime` 轮询任务并发出 `sa-dispatch`，再由 `public/native/app.js` 创建后台代理。仅在 Host 中把未打开项目的任务写入文件，仍不能证明它们已经执行。

## 实现边界与顺序

1. 将规则和任务文件的格式、修订号、大小限制、锁、备份和原子写入语义定义为跨 Rust/TypeScript 的单一持久化契约。Host 读取损坏文件时保留原文件并报告该工作区失败；不能把损坏文件当空列表。与现有 Pi 扩展并发写入时，双方必须使用相同锁路径和冲突处理。
2. Host 调度服务读取实时工作区注册表，按工作区单独记录扫描结果。对到期规则生成由工作区、规则 ID 和到期时间决定的稳定任务 ID，在任务文件中确认不存在后再入队。任务写入成功而规则历史更新失败时，下轮根据稳定 ID 补写历史，不再创建第二个任务。
3. 调度服务应有明确的单实例生命周期和停止信号；页面定时器不应与 Host 对同一规则同时入队。Windows/macOS/Linux 的时间、时区、休眠唤醒和离线目录语义要有共同定义。
4. 把未打开项目的任务交给与窗口无关的派发器；它要负责启动或复用目标 Pi 实例、审批门控、状态回写、完成通知、失败重试和应用退出时的取消或恢复。`sa-dispatch` 可继续作为 UI 入口，但不能是全工作区任务执行的唯一入口。
5. UI 显示每个工作区最近扫描时间、失败原因和待审批/执行数量。不能把“任务已入队”显示成“已经执行”。保留手动打开项目核查和恢复入口。

## 待验证的风险

- 现有规则的 `nextRunAt` 是 ISO 时间；每日规则的下次时间由本地时区计算。跨夏令时或用户变更时区时，需要先确定补跑和跳过策略。
- 同一工作区可有多个窗口和 Pi 实例，Host 调度与旧页面调度并行会重复竞争。稳定任务 ID 加文件锁用于防重，但必须验证任务、历史与审批状态的崩溃恢复。
- 规则的 `targetProject` 可指向不同于规则存储工作区的目录。调度归属、任务文件归属、执行目标和授权边界必须分别记录；目标目录不存在时应留下可见失败，不应静默派发到当前工作区。
- 用户的项目目录可能位于网络盘或移动盘；单一失败目录不能阻塞其他工作区，也不能无限重试形成负载。

## 初始调查结论（历史）

现有页面定时器和会话列表无法覆盖未打开的工作区；完整实现需要 Host 持有调度与派发生命周期，并与 Pi 扩展共享持久化契约。当前代码仅提供只读范围清单，没有声称全工作区调度已可用，也没有运行测试。

## 后续进展：子代理完成事件恢复

- Host 生命周期现在订阅本机 Pi 运行时广播，不依赖当前 WebView 的工作区。子代理正式会话绑定及最终 `agent_end` / `agent_settled` 到达时，按 `dispatch.childInstanceId` 扫描已注册工作区的正式任务文件，确认唯一归属后用共享修订号和文件锁更新原任务。

### 页面与 Host 同时处理结束事件

- 若子运行时仍有窗口连接拥有，Host 把完成回写延后两秒，优先让页面写入并发出已有的应用通知；没有窗口拥有时立即处理。延后任务由 Host 生命周期跟踪，应用停止时取消，事件接收循环不等待文件扫描。
- 同一子实例的 `agent_end` 与 `agent_settled` 只安排一份恢复工作。新的 `agent_start` 使上一轮延后工作失效；写入前还检查任务在结束事件之后是否已有 `answered` 记录，避免旧结束事件覆盖用户的继续回答。文件修订号与状态门槛仍是最后一道并发保护。
- 两秒只是页面优先窗口，不保证任何设备上的通知都到达。运行时事件遗漏、Host 重启后的孤儿任务和真实跨平台时序仍待验收。

## 后续进展：Host 派发已入队的自动化任务

- Host 生命周期每三秒扫描实时注册表中的正式任务文件，每轮最多认领八个 `pending` 且 `automation.autoDispatch === true` 的任务。审批任务不会自动派发；只接受已注册、可访问且与 `targetProject` 对应的项目目录。无效目标转为可见的 `blocked`，等待用户打开项目并恢复任务。
- 认领在任务文件修订号和同一独占锁下完成，写入唯一子实例 ID、目标工作区与 `hostManaged` 标记后才启动内嵌 Pi。目标 Pi 使用现有 `programming` 场景、运行时隔离和插件 Broker，发送与页面派发同结构的项目任务提示词；随后尝试绑定正式会话 ID。窗口中的自动派发与 Host 同时读到待处理任务时，只有一个认领写入能成功。
- 启动子进程失败会把仍由该实例认领的任务标为失败。提示词 RPC 的接受结果不确定时保留运行中任务及子实例引用，避免盲目重发造成双执行；这种孤儿任务的超时恢复仍待实现。
- Host 认领的任务由运行时 `message_end` 事件记录费用与事件序号，达到正数预算时标为失败并请求中止子代理。页面派发的任务仍由页面记录费用，`hostManaged` 边界用于防止两端重复累计。当前无窗口时的预算通知和真实费用事件验证仍待补。
- 这一步处理的是**已经入队**的自动化任务。所有已注册工作区的到期规则自动入队尚未接入 Host，页面当前工作区定时器仍在运行；审批、重试、应用重启后的孤儿恢复和三平台实机运行需要继续完成。本轮没有运行测试。

## 后续进展：Host 到期规则入队

## 后续进展：运行中任务的丢失进程识别

- Host 每分钟检查最多三十二条由 Host 认领、仍为 `running` 且已启动至少两分钟的自动化任务。检查使用本进程持有的 Pi 子进程句柄，而不只看可能滞留的运行时状态记录。
- 子进程已不在或已退出时，原任务以 CAS 更新为 `blocked`，记录 `runtime_missing` 事件和 `orphanedAt`，保留子实例与会话引用供用户检查。结果未知时不自动重跑，避免对项目或外部服务重复执行操作；用户确认后可通过现有任务恢复入口重新入队。

- 自动化中心的全工作区状态清单增加 `blocked` 计数，并将旧的“只检查当前工作区”说明改为应用打开期间检查已注册工作区。任务中心现有的“重试并运行”入口可处理 `blocked` 任务，重试会重置旧子实例引用；用户仍需先核对原会话是否已产生结果。

## 后续进展：无窗口的运行结果与自动重试

- Host 增加全工作区规则运行结果核对：规则最新历史为 `queued` 或 `retry_queued` 时，对照任务状态，补写 `completed`、最终 `failed` 或新一轮 `retry_queued`。轮询按工作区和规则轮转，每轮处理上限，避免一个持续出错的工作区长期占满扫描配额。
- 符合重试上限且未触及费用预算的失败任务，由 Host 以任务文件 CAS 重新入队。重试清掉旧子实例、会话和启动时间，使后台派发器能认领新一轮；达到费用预算的任务不会自动重试。页面侧同一重试路径也清掉旧子实例引用，修正了“待派发但永远跳过”的状态。
- 重试事件时间和任务完成时间成为规则历史的稳定运行 ID。若任务已再次派发甚至已完成，而规则历史写入未成功，Host 仍能先从 `automation_retry` 事件恢复重试历史，再处理完成结果。页面侧也使用任务完成时间记录结果，减少与 Host 并发更新时的重复历史。
- 缺失 `requireApproval` 的旧规则继续按 Pi 的默认语义要求审批；不会被 Host 当成免审批任务自动派发。静态编译和前端类型检查已通过；真实多窗口并发、崩溃窗口、审批通知与三平台实机行为仍未验证。本轮没有运行测试。

## 后续进展：扫描公平性与关闭边界

- Host 派发器原先每轮只从排序最前的任务文件取八条候选；若前面的目录持续积压或反复报错，后面的工作区可能长期得不到机会。现按扫描轮次轮转工作区和任务起点，每个工作区每轮最多取两条，仍保留总量上限。
- 规则入队、运行结果核对和丢失进程扫描也按轮次轮转，并限制单工作区配额。Host 停止时，阻塞扫描在工作区或任务边界检查生命周期信号，不继续处理整轮候选。已经开始的一次文件操作仍可能完成；任务先写入、规则历史后补记的恢复设计继续覆盖这段窗口。
- `cargo check --all-targets` 已通过；轮转顺序、停止时文件写入窗口和多平台真实运行仍需实际验证。本轮没有运行测试。
- 每日规则遇到夏令时前跳造成的不存在当地时间时，Host 现按时钟跳变长度顺延，例如 `02:30` 跳过一小时后得到 `03:30`，与页面 `Date.setHours` 的常见语义一致；重复的当地时间选较早一次。跨时区变更与各平台时区数据库的实际差异仍待实机核对。

- 子代理结束事件由 Host 成功回写任务后，按完成、失败或待输入状态发出通知；若页面先完成同一任务，Host 不会再次写入或通知。Host 费用预算触顶且成功标记失败时也发出通知。通知只包含状态和有界任务标题，不包含任务描述、模型输出或错误正文。
- 现有 `notify-rust` 后端被 Host 复用，入口仍为 best effort；Windows/macOS/Linux 的通知权限、系统服务、展示及与页面并发时的实际去重尚未实机验证。Rust 静态编译与前端静态检查通过，本轮没有运行测试。
- 目标项目不可访问或未注册、子代理启动失败、以及运行中子进程丢失时，Host 在对应任务文件成功转为 `blocked` / `failed` 后提示“需要检查”或“失败”。冲突或已由其他窗口更新导致没有写入时不发通知。

## 后续进展：跨工作区待办入口与运行时前端同步

- 自动化中心的已注册工作区清单为可访问目录提供“打开任务”。桌面端调用已有 `switch_window_workspace`，把当前窗口切到该项目并保留 `com.zicode.tasks` 应用路由；失败时在当前页面显示错误。目录不可用的行不显示按钮。LAN/移动端没有本机 Tauri 命令，也不显示此入口。
- 入口使用清单中的已注册路径，不接受用户在页面自由输入路径；目标命令会再次检查目录并按现有工作区启动流程建立会话。跨工作区审批与阻塞任务因此有明确的人工检查入口。
- 先前只运行前端静态检查导致 `public/native/react/automation.js` 构建产物仍带旧文案与旧计数。此次 `bun run build:react` 后确认运行时 bundle 包含全工作区说明、阻塞数量和新按钮；`bun run typecheck`、`bun run check` 通过。没有运行测试或桌面实机点击验证。

## 后续进展：审批入口对应实际任务

- 自动化中心读取当前工作区的正式任务文件，按 `pending` 且未自动派发的自动化任务建立规则到待审批任务的映射。规则卡片、待审批筛选和数量都依据该映射，不再依赖入队后已清空的旧 `approvalPending` 标志。多条待审批任务按文件顺序逐条处理，每次审批后刷新映射。
- 卡片“批准并运行”调用任务中心的已有任务审批路径；任务中心先刷新文件并确认该 ID 仍为 `pending`，写入派发状态成功后才发出 `sa-dispatch`。旧 `runWorkflow(..., "approval")` 调用也转到同一路径，避免额外创建一条任务。
- 任务文件读取失败时给出错误提示并禁用规则卡片的“立即运行”，防止误把未知的待审批任务当作没有任务。桌面端通过组合根接入任务中心，单独挂载自动化视图时跳转到任务中心对应任务。
- 前端 `bun run typecheck`、`bun run check`、`bun run build:react` 通过，运行时 bundle 已同步；原有审批测试的期望已按“批准已有任务”语义调整，但本轮没有运行测试。审批操作的真实派发、并发与三平台运行仍无实机证据。

### 审批时固定来源工作区

- 任务中心的审批操作现在按点击时捕获的运行时目标重新读取正式任务文件，确认指定任务仍为 `pending`，再用同一目标和读到的修订号写入。页面切换工作区不会把旧列表或旧修订号写到新工作区。
- 审批成功后的 `sa-dispatch` 事件携带同一个来源目标，原生派发器据此回写原工作区的任务文件；若用户在异步写入期间切到另一项目，派发不再误用新项目作为任务来源。当前视图已经切换时也不会用旧工作区列表覆盖任务中心状态。
- 审批读写逻辑集中在 `frontend/src/features/tasks/approve-task.ts`。任务中心卡片和自动化规则入口共用它；手动重试、暂停等其他任务操作尚未统一固定目标，仍是后续工作。仅完成静态检查，真实切换时序和桌面派发尚未运行验证。

### 任务中心列表随工作区切换

- 任务中心原先 `setTarget()` 为空；跨项目切换后可短暂显示旧项目任务，旧轮询响应也能覆盖新项目列表。现在切换目标时清空列表、修订号、焦点和创建请求，并让新的读取固定使用新运行时目标。
- 每次读取记录目标轮次。旧轮次响应、错误及完成状态均不再写入新视图；切换时可立即启动新读取，不等待旧请求结束。项目路径建议也按同一目标读取并丢弃旧轮次结果。
- 任务中心的页面定时模板扫描在写入前检查目标轮次，并固定使用扫描开始时的目标；旧扫描结束后会补触发一次新目标扫描。其他任务修改入口的异步目标边界尚待逐步统一。当前仅做静态检查，未运行跨项目交互验证。

### 任务修改固定目标

- 创建请求在入队时记录工作区轮次。若真正执行前已切换项目，请求会报错并要求重试；读取后到写入前再次核对轮次，写入固定使用读取时的目标，切换后不把旧结果发布到新列表。
- 编辑、立即运行定时模板、置顶、归档、删除、清理已完成任务和手动重试等修改入口捕获任务列表、修订号与工作区目标，按捕获目标写入。写入完成时若界面已切到其他工作区，仅保留原项目的持久化结果，不覆盖新列表。重试派发事件也携带原项目来源目标。
- 回答、暂停和取消任务在等待子代理操作前捕获同一写入上下文；后续任务状态更新沿用原项目目标。任务文件的 CAS 仍会拒绝中途被别的窗口修改过的旧快照，冲突需要用户刷新后再操作。
- 仍需三平台实机验证并发、切换和子代理停止时序；本轮未运行测试。
- `bun run typecheck`、`bun run check` 通过。首次并行构建 React bundle 时，Windows 报输出文件映射占用；随后单独运行 `bun run build:react` 成功，运行时 `tasks.js` 已更新。没有因此结束应用或删除构建文件。
