# 2026-09-30 自动化规则并发保存

状态：代码、前端类型检查、目标模块类型检查、扩展与 React 构建、静态规则检查通过；真实多窗口及跨平台验收待补。

## 发现与目标

自动化规则文件原先采用读全量、修改、直接覆盖的写法。两个窗口或调度器同时更新时，较晚写入可覆盖另一方的新规则或运行历史；损坏文件读取时被当作空列表，后续保存可能抹去原内容。草稿文件已有独立保护，但不覆盖正式规则。

## 修改与决策

- 正式规则读取返回原文件字节的 SHA-256 修订号；损坏、超限、重复或缺失 ID 的文件明确报错，保留原文。
- 写入必须携带预期修订号，在工作区文件的独占锁内重读、比较、更新，并经同目录临时文件刷盘及原子替换。限制 200 条规则、8 MiB；旧客户端无版本写入被拒绝。
- 新工作区文件优先，尚未迁移的旧文件仍可读取；首次成功写入新路径后保留旧文件，避免迁移失败时遗失来源。旧版进程若绕过新锁直接写同一路径，仍不受此机制约束。
- 前端保存和删除携带读取修订号；冲突要求刷新，不自动覆盖。运行历史使用固定运行 ID，并在冲突或短暂锁繁忙时有限次重读重试，避免重复记录。
- 新建表单在挂载时生成稳定规则 ID。同一表单在响应丢失后重试，会先读取原工作区并比较已保存字段；相同内容确认成功，ID 相同但内容不同则要求刷新，不创建第二条规则。
- 编辑已有规则时，服务端仅合并表单可编辑字段；运行历史、最近执行时间和审批状态取锁内最新值。只有启用状态或计划字段变化才使用表单新算的下次运行时间，避免刷新后重试覆盖调度器的历史和时间。
- 计划触发的任务 ID 由规则 ID 和本轮到期时间确定。历史回写失败后，下次轮询遇到已存在的任务会尝试补写原轮次历史，不再生成第二个任务；手动执行仍使用新 ID。
- 异步配置请求固定到启动时的 Pi 目标；切换项目后，已提交任务尽力在原项目补写历史，当前界面不接收旧作用域结果。
